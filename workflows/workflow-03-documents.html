📄 Document Upload & Verification

CP Driver uploads required CDL, medical, and truck-compliance documents during onboarding

📋 Workflow Goal

Enable CP Driver drivers to upload required documents — CDL, Medical Certificate, Vehicle Registration, Insurance, Inspection/Safety, and Operating Authority — as part of the driver onboarding step flow (Driver.onboardingStep). Documents are stored in a dedicated Document collection, one current document per {driverId, docType} pair — re-uploading a document type replaces the previous file rather than keeping version history. This workflow ensures all applicable documentation is collected before a driver can be submitted for admin approval (workflow-05-driver-approval.html).

⚠ No AI/OCR verification is wired up yet. Documents are stored with status: 'pending' and sit there until an admin reviews the driver as a whole (approveDriver/rejectDriver) — there is currently no automated OCR/AI verification pipeline and no per-document approve/reject endpoint. See workflow-04-ai-verification.html for the intended future state of automated verification.

📱 Frontend Pages

CP Driver Mobile App (React Native — vcg_driverr)

  • CDL Information: onboarding/CdlInformationScreen.jsx — CDL fields plus a required CDL photo/PDF upload (file field cdlDocument)
  • Driver Qualification: onboarding/DriverQualificationScreen.jsx — years of CDL experience, medical cert status/expiry, an optional medical cert photo upload (file field medicalCertDocument), MVR consent checkbox (required to continue), road test status/notes
  • Truck Documents: onboarding/TruckDocumentsScreen.jsx — registration and insurance uploads (required), inspection upload (optional), operating authority upload with a "Not applicable" toggle (optional/conditional)
  • Document Status: documents come back on GET /api/drivers/me / GET /api/drivers/me/documents with a status per document (pending / approved / rejected), shown on the relevant onboarding screen and on onboarding/PendingApprovalScreen.jsx
  • Re-upload: re-submitting the same onboarding step's file field simply overwrites the prior document (no separate delete/re-upload screen — it's the same upload control)

TruckAdmin Dashboard

  • Driver Detail View: pending/incomplete/approved/rejected driver lists are populated with each driver's documents array (see workflow-05-driver-approval.html) so an admin can open a driver and view their uploaded CDL / Medical Cert / Registration / Insurance / Inspection / Operating Authority files
  • Not yet built: there is no dedicated per-document review page, preview modal, or per-document approve/reject action today — verification is currently all-or-nothing at the driver level via PUT /api/admin/drivers/:id/approve / /reject

🔌 API Endpoints

GET /api/drivers/me/documents

requireAuth + requireRole('driver'). Returns { success: true, data: Document[] } — every document currently on file for this driver.

GET /api/drivers/me

Also returns a documents array alongside the driver profile (and populates truckId).

PUT /api/drivers/me/cdl-info

Multipart, file field cdlDocument. Upserts the driver's cdl document (JPG/PNG/PDF, 8MB max) alongside the CDL info fields; sets expiresAt to the CDL expiry.

PUT /api/drivers/me/qualification

Multipart, file field medicalCertDocument (optional). Upserts the driver's medical_cert document if a file is included; sets expiresAt to the medical cert expiry.

PUT /api/drivers/me/truck-documents

Multipart, file fields registration / insurance / inspection / operatingAuthority — only the fields actually present in the request are uploaded/upserted, mapping to docType values vehicle_registration / insurance / inspection / operating_authority respectively. Advances onboardingStep to 'agreements'.

Not implemented: there is no DELETE endpoint and no per-document verify endpoint. "Re-upload" is just calling the same step endpoint again with a new file — upsertDocument overwrites the existing {driverId, docType} record, resets status to 'pending', and clears rejectionReason / reviewedAt / reviewedBy.

Request Example: CDL Information (info + document in one call)

PUT /api/drivers/me/cdl-info Headers: { "Authorization": "Bearer eyJhbGc...", "Content-Type": "multipart/form-data" } Form fields: { "licenseNumber": "TX-88213456", "cdlState": "TX", "cdlClass": "A", "endorsements": ["H", "N"], "licenseExpiry": "2029-04-12", "cdlDocument": (file: cdl_front.jpg) }

Request Example: Truck Documents

PUT /api/drivers/me/truck-documents Headers: { "Authorization": "Bearer eyJhbGc...", "Content-Type": "multipart/form-data" } Form fields: { "registration": (file: registration.pdf), "insurance": (file: insurance_cert.pdf), "inspection": (file: annual_inspection.jpg) // "operatingAuthority" omitted — driver marked "Not applicable" in-app }

💾 Database Models

Document Model (documents collection) — actual implementation

Field Type Description
driverId ObjectId Reference to Driver, required, indexed
ownerType String enum: ['driver', 'truck'] — which entity the document belongs to
docType String enum: ['cdl', 'medical_cert', 'vehicle_registration', 'insurance', 'inspection', 'operating_authority']
fileUrl String Required. Relative path, e.g. uploads/drivers/1735689600000_cdlDocument.jpg (local disk, served via /uploads static route — not S3)
fileName String Original uploaded filename
status String enum: ['pending', 'approved', 'rejected'] (default 'pending') — no automated process sets this today; see caveat above
rejectionReason String Schema field exists, not currently set by any controller
expiresAt Date Set from CDL expiry / medical cert expiry on upload; not set for truck documents
reviewedAt / reviewedBy Date / ObjectId Schema fields exist (reviewedBy refs User), not currently set by any controller
createdAt / updatedAt Date Timestamps

Unique compound index on {driverId, docType} — there is at most one current document per type per driver. Uploading again for the same docType replaces the existing record (no version history is kept).

Required Documents (by onboarding step)

Document Type (docType) Required to submit? Uploaded during Format / Max Size
CDL (cdl) Yes CDL Information step JPG, PNG, PDF — 8 MB
Medical Certificate (medical_cert) No — optional at the API level, even though the screen prompts for it Qualification step JPG, PNG, PDF — 8 MB
Vehicle Registration (vehicle_registration) Yes Truck Documents step JPG, PNG, PDF — 8 MB
Insurance (insurance) Yes Truck Documents step JPG, PNG, PDF — 8 MB
Inspection / Safety (inspection) Optional Truck Documents step JPG, PNG, PDF — 8 MB
Operating Authority (operating_authority) Conditional — the app offers a "Not applicable" toggle for drivers who don't operate under their own DOT authority Truck Documents step JPG, PNG, PDF — 8 MB

Submission gate (PUT /api/drivers/me/agreements) only hard-requires the CDL info fields + CDL document, a linked truck, and the registration + insurance documents — missing any of those returns 400 { message: 'Onboarding is incomplete', missing: [...] }. There's no such hard check for the medical certificate, inspection, or operating authority documents.

⚙️ Implementation Flow

Document Upload Flow (Truck Documents example)

  1. Driver reaches the Truck Documents screen (onboardingStep: 'truck_documents')
  2. App fetches current status via GET /api/drivers/me or /api/drivers/me/documents
  3. Driver picks files for Registration and Insurance (required); optionally Inspection and Operating Authority, or toggles "Not applicable" for Operating Authority
  4. App opens camera or gallery picker per field
  5. On confirm, app submits one multipart PUT to /api/drivers/me/truck-documents with whichever file fields were filled in
  6. Backend saves each file to local disk (multer), then upserts one Document per field present with status: 'pending'
  7. Backend advances Driver.onboardingStep from 'truck_documents' to 'agreements'
  8. Response returns the updated driver + full documents array
  9. Driver proceeds to Agreements; no automated verification runs at this point (see caveat above)

File Upload Process (Backend, actual)

  1. Receive multipart/form-data request
  2. requireAuth + requireRole('driver') validates the JWT and role
  3. Multer fileFilter validates MIME type — only image/jpeg, image/png, application/pdf accepted
  4. Multer limits.fileSize enforces an 8 MB cap (same limit for every document type — there is no smaller limit for any particular doc)
  5. Multer diskStorage writes the file to uploads/drivers/, filename {Date.now()}_{fieldname}{ext} (e.g. 1735689600000_cdlDocument.jpg)
  6. upsertDocument() runs Document.findOneAndUpdate({ driverId, docType }, {...}, { upsert: true }) — creates the record on first upload, overwrites it (and resets status to pending, clears any prior rejection) on re-upload
  7. No AI/OCR verification job is queued — the "next workflow" trigger described in the old India-market version of this doc does not exist yet (see workflow-04-ai-verification.html)
  8. Return document/driver details to client

Document Re-upload Flow (actual)

  1. Driver revisits the relevant onboarding step screen (CDL Info / Qualification / Truck Documents)
  2. Picks a new file for the same field and re-submits the same PUT endpoint
  3. upsertDocument() overwrites the existing {driverId, docType} record in place — old file on disk is not deleted, just orphaned; there's no explicit delete step and no separate "old document" bookkeeping

📐 Business Rules & Validation

  • Required at submission: CDL info + CDL document, a linked truck, vehicle registration document, and insurance document — enforced server-side by PUT /api/drivers/me/agreements (returns 400 with a missing[] list otherwise)
  • Not hard-required: medical certificate document, inspection document, operating authority document — the app prompts for them but the server doesn't block submission if they're absent
  • File Format: JPG, PNG, or PDF — same rule for every document type
  • File Size: 8 MB max — same limit for every document type
  • One document per type: unique {driverId, docType} index — re-uploading replaces the prior document, no version history kept
  • Re-upload Limit: none enforced — a driver can re-upload a given document type any number of times
  • Edit Restriction: none enforced — a document can be re-uploaded even after status: 'approved', since nothing currently sets that status anyway (see caveat above)
  • Expiry Check: expiresAt is stored for CDL and medical cert documents, but nothing currently blocks trips or re-triggers review when a document is expired
  • Not implemented: minimum image resolution check, storage-duration/retention policy, and any access-control layer beyond standard JWT auth

🔒 Security Considerations

⚠ Storage is local disk, not encrypted cloud storage. The India-market version of this doc described AWS S3 with AES-256 encryption, signed URLs, antivirus scanning, and EXIF stripping — none of that exists in the current implementation. Files are written to a local uploads/drivers/ directory on the server and served back via app.use('/uploads', express.static(...)) — a plain, unauthenticated static file route. Anyone with a document's fileUrl path can fetch it without a JWT. This should be treated as a known gap, not a documented feature.
  • Authorization to upload: JWT + requireRole('driver') required; a driver can only write to their own Driver record (looked up via req.user._id)
  • Authorization to read a file: none — /uploads is a public static route, not gated by auth or ownership
  • File type validation: multer fileFilter restricts to JPG/PNG/PDF
  • File size validation: multer enforces an 8 MB cap
  • Not implemented: encryption at rest, signed/expiring URLs, antivirus scanning, EXIF stripping, upload rate limiting, audit logging of uploads, backups/versioning, and any data-retention/deletion policy

📂 File Storage Structure

Local Disk Layout (actual)

vcg_backend/ └── uploads/ └── drivers/ ├── 1735689600000_cdlDocument.jpg ├── 1735689610000_medicalCertDocument.pdf ├── 1735689620000_registration.pdf ├── 1735689630000_insurance.pdf ├── 1735689640000_inspection.jpg └── 1735689650000_operatingAuthority.pdf

All drivers' files sit in one flat uploads/drivers/ directory (no per-driver or per-docType subfolders) — the Document.driverId + docType fields in the database are what associate a file back to a specific driver, not the file path.

Naming Convention

{Date.now()}_{multerFieldName}{ext}

Example: 1735689600000_cdlDocument.jpg. The field name is the multipart form field (cdlDocument, medicalCertDocument, registration, insurance, inspection, operatingAuthority) — not the docType enum value, and not tied to the driver's name or ID.
