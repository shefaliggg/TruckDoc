🔐 User Registration & Login

Account creation and authentication for CP Driver (US), CP Shipper (US), and TruckAdmin

🎯 Workflow Goal

Objective: Secure, role-appropriate account creation and login for all three apps.

Scope note: CP Driver (vcg_driverr) and CP Shipper (vcg_user) both target the US market and use a passwordless phone/email + OTP flow (sections below). CP Shipper is the renamed/redesigned TruckUser customer app — its old email + password screens are superseded by the OTP flow. Company name, business address, EIN, tax info, payment info, and pickup/delivery locations are not collected during CP Shipper auth — they belong to the separate Shipper Profile Creation step (Personal, Business, Locations) covered by workflow-02-profile.html. Likewise, driver's license, DOT info, truck details, insurance, and banking belong to the Driver Profile & Verification workflow (workflow-02-profile.html, workflow-03-documents.html). India-market fields (Aadhaar, PAN, GSTIN, IFSC, PUC, +91 numbers) do not apply to either US flow. TruckAdmin is unaffected and keeps the existing email + password flow — see Legacy Auth at the bottom of this page.

🔌 API Endpoints Required

CP Driver (US, phone/email + OTP) — actual implementation

There is one shared pair of endpoints for both send and verify, not separate per-channel/per-role routes — the channel is selected by a channel field in the request body, and there's no separate "resend" route: calling send again is the resend (subject to the 60-second cooldown below).
  • POST /api/auth/otp/send - body { channel: 'email' | 'phone', email?, phone? }. For channel: 'email': validates email format, enforces a 60s resend cooldown per identifier, generates a 6-digit code (hashed, 10 min expiry), emails it via Resend. Returns 200 { success: true, message }, or 429 if within the cooldown window. For channel: 'phone': always returns 501 { success: false, smsAvailable: false, message } (no SMS provider configured — see caveat above).
  • POST /api/auth/otp/verify - body { channel: 'email' | 'phone', email?, phone?, code? }. For channel: 'email': checks the hashed code against the most recent unexpired, unconsumed OTP for that identifier (max 5 attempts before 429), then auto-detects new vs. existing user by email. If new: creates the User (role: 'driver', authMethod: 'email_otp', emailVerified: true) and a matching Driver record (approvalStatus: 'incomplete', onboardingStep: 'driver_info'). Returns 200 { success: true, token, user, isNewUser, driver: { approvalStatus, onboardingStep } }. For channel: 'phone': always returns the same 501 stub as send.
  • GET /api/auth/me - generic (not driver-specific), requireAuth. Returns { success: true, user: { id, firstName, lastName, email, phone, role, createdAt } } — no onboarding/approval status here (use GET /api/drivers/me, see workflow-02-profile.html, for approvalStatus / onboardingStep).

CP Shipper (US, phone/email + OTP)

  • POST /api/auth/shipper/phone/send-code - Send 6-digit SMS OTP to a US (+1) number
  • POST /api/auth/shipper/phone/verify - Verify phone OTP; returns JWT + isNewShipper
  • POST /api/auth/shipper/email/send-code - Send 6-digit email OTP
  • POST /api/auth/shipper/email/verify - Verify email OTP; returns JWT + isNewShipper
  • POST /api/auth/shipper/resend-code - Resend OTP (rate-limited)
  • GET /api/auth/shipper/me - Get current shipper + accountStatus

TruckAdmin — unchanged

  • POST /api/auth/register - Create new user account
  • POST /api/auth/login - Authenticate user and return JWT token
  • GET /api/auth/me - Get current logged-in user details
  • PUT /api/auth/update-password - Update user password
  • POST /api/auth/forgot-password - Request password reset

🗄️ Database Models Needed

User Model (CP Driver, US) — actual implementation, passwordless-capable

This is the real User collection (shared by all roles), not a separate Driver auth model. Driver-specific onboarding fields (CDL, address, truck, agreements, etc.) live on the separate Driver profile — see workflow-02-profile.html.
  • authMethod: enum ['password', 'email_otp', 'phone_otp'] (default: 'password')
  • firstName / lastName: string, optional (not required — a fresh OTP signup has neither until the Driver Information step)
  • email: string, lowercase, sparse unique, optional
  • phone: string, sparse unique, optional
  • passwordHash: string, optional (not set for OTP-created accounts)
  • role: enum ['user', 'driver', 'admin'], required
  • isPhoneVerified: boolean (default: false)
  • emailVerified: boolean (default: false) — note: no separate isEmailVerified field, this is the existing field, reused
  • createdAt / updatedAt: Date
  • No Aadhaar/PAN/GSTIN/IFSC/PUC fields — not applicable to the US market. There is no accountStatus enum on this model; driver progress/approval state lives on Driver.onboardingStep and Driver.approvalStatus instead (see workflow-02-profile.html, workflow-05-driver-approval.html) — the "Account Status States" section below describes the intended UX states conceptually, but they are derived/mapped from those two Driver fields, not stored as a single enum.

Shipper Model (CP Shipper, US) — passwordless

  • authMethod: enum ['phone', 'email']
  • phone: string, E.164 US format (+1XXXXXXXXXX), unique, nullable — becomes primary operational contact once profile is complete
  • email: string, unique, nullable
  • isPhoneVerified: boolean (default: false)
  • isEmailVerified: boolean (default: false)
  • accountStatus: enum ['profile_incomplete', 'verification_pending', 'action_required', 'approved', 'suspended']
  • createdAt / updatedAt: Date
  • No password field. Personal / business / location details live on the Shipper Profile (workflow-02-profile.html), not here.

OtpCode Model — actual implementation (currently backs CP Driver only)

  • identifier: string — lowercased email, or E.164 phone (no separate ownerType/ownerId — the record isn't linked to a User until verify succeeds)
  • channel: enum ['email', 'phone']
  • codeHash: string, sha256 (hashed, never stored in plaintext)
  • purpose: enum ['signup_login'] (default)
  • expiresAt: Date (10 min TTL)
  • attempts: number (default 0, max 5 before lockout)
  • consumedAt: Date, nullable
  • Only channel: 'email' records are ever actually created today — the phone channel is rejected before an OTP record is written (see the 501 stub note above).

User Model (TruckAdmin) — unchanged

  • email: string (unique, required)
  • password: string (hashed with bcrypt, required)
  • role: enum ['admin']
  • firstName / lastName: string
  • phone: string
  • isEmailVerified / isPhoneVerified: boolean (default: false)
  • createdAt / updatedAt: Date

🔄 Implementation Flow

CP DRIVER — PHONE FLOW (UI exists, backend stubbed):
1. Driver opens Welcome screen, taps "Create Driver Account" or "Log In"
2. Chooses "Continue with Phone"
3. Enters US phone number (+1) on PhoneAuthScreen.jsx
4. API: POST /api/auth/otp/send  { channel: 'phone', phone }
   - Backend validates US phone format, then always returns
     501 { success: false, smsAvailable: false, message }
     (no SMS provider configured yet)
5. Screen shows "Phone sign-in isn't available yet — please continue with
   email" and offers a button to switch to the Email flow below

CP DRIVER — EMAIL FLOW (fully functional):
1. Driver opens Welcome screen, taps "Create Driver Account" or "Log In"
   (both lead to the same next step — the backend auto-detects new vs.
   existing user by email at verify time)
2. Chooses "Continue with Email", enters email on EmailAuthScreen.jsx
3. API: POST /api/auth/otp/send  { channel: 'email', email }
   - Validate email format, enforce 60s resend cooldown
   - Generate 6-digit OTP, hash (sha256) + store with 10 min expiry
   - Send via Resend
4. Driver enters 6-digit code on VerifyCodeScreen.jsx
5. API: POST /api/auth/otp/verify  { channel: 'email', email, code }
   - Compare hashed code, check expiry + attempt count (max 5)
   - If new email: create User (role: 'driver', authMethod: 'email_otp',
     emailVerified: true) + Driver (approvalStatus: 'incomplete',
     onboardingStep: 'driver_info')
   - If existing driver email: mark emailVerified true if not already
   - Generate JWT token
   - Return { success, token, user, isNewUser, driver: { approvalStatus, onboardingStep } }
6. Navigate based on driver.onboardingStep / approvalStatus:
   - New driver / incomplete → resume onboarding at that onboardingStep
     (see workflow-02-profile.html)
   - approvalStatus 'pending' or 'rejected' → PendingApprovalScreen.jsx
   - approvalStatus 'approved' → DriverTabs (Home)

AUTHENTICATION CHECK (app relaunch):
1. On app launch, check for stored JWT token
2. If token exists:
   - API: GET /api/drivers/me (populates truckId + documents)
   - Validate token, read fresh approvalStatus / onboardingStep
   - Route per navigation rules above (src/navigation/MainNavigator.jsx +
     onboardingSteps.js)
3. If no token or invalid: show Welcome screen

🔄 CP Shipper — Implementation Flow

CP SHIPPER — PHONE FLOW:
1. Shipper opens Welcome screen, taps "Create Shipper Account" or "Log In"
2. Chooses "Continue with Phone"
3. Enters US phone number (+1)
4. API: POST /api/auth/shipper/phone/send-code
   - Validate US phone format (E.164)
   - Generate 6-digit OTP, hash + store with 5-10 min expiry
   - Send via SMS provider
5. Shipper enters 6-digit code on Verify screen
6. API: POST /api/auth/shipper/phone/verify
   - Compare hashed code, check expiry + attempt count
   - Create Shipper record if new (isPhoneVerified = true)
   - Generate JWT token
   - Return token + isNewShipper flag
7. Navigate:
   - New shipper → Shipper Profile Creation (Personal → Business → Locations)
   - Existing shipper → Account Check → Home / Continue Setup

CP SHIPPER — EMAIL FLOW:
Same as above, using POST /api/auth/shipper/email/send-code and
POST /api/auth/shipper/email/verify in place of the phone endpoints.

ACCOUNT CHECK (existing shipper):
1. On successful verification of an existing shipper, API: GET /api/auth/shipper/me
2. Route based on accountStatus:
   - profile_incomplete   → resume Shipper Profile Creation
   - verification_pending → Verification Pending screen
   - action_required      → Action Required screen (what's missing)
   - approved             → Home
   - suspended            → Account Suspended screen

AUTHENTICATION CHECK (app relaunch):
1. On app launch (Splash), check for stored JWT token
2. If token exists:
   - API: GET /api/auth/shipper/me
   - Validate token, get fresh accountStatus
   - Route per Account Check above
3. If no token or invalid: show Welcome screen

🚦 CP Driver / CP Shipper — Account Status States

Both apps route on the same conceptual states, shown below as a single accountStatus enum for readability. For CP Driver specifically, there is no such field in the database — these states are derived from Driver.approvalStatus (incomplete/pending/approved/rejected) and Driver.onboardingStep (driver_info…submitted); see workflow-02-profile.html and workflow-05-driver-approval.html for the real fields.

profile_incomplete verification_pending action_required approved suspended

For CP Driver, these states are set by the Driver Profile & Verification workflows (workflow-02-profile.html, workflow-03-documents.html, workflow-05-driver-approval.html). For CP Shipper, they're set by Shipper Profile Creation (workflow-02-profile.html) — this auth workflow only reads and routes on accountStatus, it does not set it.

🔒 Security Considerations

CP Driver & CP Shipper (phone/email + OTP)

  • OTP Format: 6-digit numeric code, 5-10 minute expiry, hashed at rest (never stored in plaintext)
  • Rate Limiting: Limit send-code/resend-code requests per phone/email/IP to prevent SMS pumping fraud and brute force
  • Attempt Limiting: Lock out after 5 failed verification attempts, require a fresh code
  • Phone Validation: Validate as a US number (E.164, +1) before sending an OTP
  • JWT Tokens: Signed with secret key, stored in secure storage (iOS Keychain, Android KeyStore)
  • HTTPS Only: All authentication endpoints must use HTTPS
  • No Password Storage: Passwordless design removes password-related attack surface (credential stuffing, reuse) for this flow

TruckAdmin (email + password) — unchanged

  • Password Hashing: Use bcrypt with 10 rounds for password hashing
  • JWT Tokens: 7-day expiration, signed with secret key
  • Input Validation: Validate email format, password strength (min 8 chars)
  • Rate Limiting: Limit login attempts to prevent brute force attacks
  • Secure Storage: Store JWT tokens in secure storage (iOS Keychain, Android KeyStore)
  • HTTPS Only: All authentication endpoints must use HTTPS

REGISTRATION FLOW:
1. User opens Registration Screen
2. Fills in: First Name, Last Name, Email, Phone, Password, Role
3. Clicks "Create Account"
4. API: POST /api/auth/register
   - Validate input data
   - Hash password (bcrypt with 10 rounds)
   - Create User record in database
   - Send verification email
5. Return success response
6. Navigate to Login Screen

LOGIN FLOW:
1. User opens Login Screen
2. Enters Email and Password
3. Clicks "Login"
4. API: POST /api/auth/login
   - Find user by email
   - Compare password with hashed password
   - Generate JWT token (expires in 7 days)
   - Return token + user data
5. Store token in secure storage
6. Navigate to Home Screen based on role
   - Customer → Bookings Screen
   - Admin → Dashboard

AUTHENTICATION CHECK:
1. On app launch, check for stored JWT token
2. If token exists:
   - API: GET /api/auth/me
   - Validate token
   - Get fresh user data
   - Navigate to appropriate home screen
3. If no token or invalid:
   - Show Login Screen
